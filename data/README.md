# Step 2 Data Documentation — Time-Table Optimizer

## Project purpose

The Time-Table Optimizer is a learning project that prepares timetable problem scenarios for comparison of a simple baseline method and a later Genetic Algorithm.

## Data source

This Step 2 dataset is **team-generated simulated scenario data**. It is not downloaded from, or claimed to represent, a real university timetable.

The generator uses the assumptions already established in Step 1:
- Courses: C01 to C05
- Cohorts: G1 and G2
- Faculty: F1 to F3
- Weekly sessions: 1 to 4
- Duration: 1 or 2 slots
- Room types: classroom or lab
- Room capacities: classroom 60, lab 30
- Time slots: S1 to S10

## Licence / provenance

No external dataset licence applies because these records are generated by the team for academic learning. The generator code in `src/generate_scenarios.py` is the reproducible source process.

## Step 2 scenario design

The valid Step 2 source contains:
- 10,000 distinct timetable scenarios
- 5 course records per scenario
- 50,000 valid course records after cleaning
- 7,000 normal scenarios
- 2,000 boundary scenarios
- 1,000 stress scenarios

A separate invalid-test file contains 100 intentionally invalid scenarios (500 course records). These are testing evidence only and are never included in the cleaned scenario dataset.

### Scenario categories

**Normal** — ordinary values inside the Step 1 ranges.

**Boundary** — values close to the allowed limits, such as 3–4 weekly sessions and varied 1–2-slot durations.

**Stress** — high scheduling pressure using 4 weekly sessions and 2-slot durations, with repeated faculty/cohort patterns that make scheduling harder while keeping the input values within valid data ranges.

**Invalid** — intentionally broken records used to prove validation catches errors, for example an invalid course, faculty, weekly-session count, duration, or slot.

## Fields

| Field | Meaning | Type / unit | Rule |
|---|---|---|---|
| scenario_id | Unique timetable problem scenario | text | TTO-00001 to TTO-10000 for valid data |
| case_type | Scenario difficulty/test category | category | normal, boundary, or stress in the valid file |
| course_id | Course code | text | C01 to C05 |
| cohort_id | Student group | text | G1 or G2 |
| faculty_id | Teacher | text | F1 to F3 |
| weekly_sessions | Sessions required per week | whole number | 1 to 4 |
| duration_slots | Length of one session | slots | 1 or 2 |
| required_room_type | Room type required | category | classroom or lab |
| room_capacity | Candidate room capacity | whole number | classroom 60, lab 30 |
| room_type | Candidate room type | category | classroom or lab |
| slot_id | Time-slot value used in the scenario record | text | S1 to S10 |

## Why scenario_id is repeated

Each scenario contains five rows, one for each course C01–C05. The same `scenario_id` groups those five course records into one timetable problem instance.

## Raw-data rule

Files in `data/raw/` are the original generated source files. They should not be manually edited. Cleaning is performed on an in-memory copy and the processed result is written under `data/processed/`.

## Step 2 pipeline

1. Generate reproducible scenario data with seed 42.
2. Keep the raw generated CSV unchanged.
3. Inspect shape, columns, missing values and duplicates.
4. Clean only the in-memory copy.
5. Validate required fields, value ranges, scenario completeness and duplicate status.
6. Save cleaned valid scenarios under `data/processed/`.
7. Keep invalid testing scenarios separate.
8. Record the results in the Step 2 reports.

## Limitation

These scenarios are simulated educational inputs. They are not observations of any real university timetable. They are intended to test data preparation and later scheduling algorithms.

## Safety / academic honesty note

No generated timetable scenario should be described as a real university record. The generated files are testing and demonstration data only.
